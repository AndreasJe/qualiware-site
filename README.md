# QualiWare marketing site

One Next.js 16 application with Payload CMS 3 installed directly into it — a
single server process, a single database, and four properties served from one
deployment:

| Property | Tenant | Content |
| --- | --- | --- |
| `qualiware.com` | `main` | Marketing site, pricing, resources, case studies |
| `docs.qualiware.com` | `docs` | Documentation & wiki — open, no login wall |
| `partners.qualiware.com` | `partners` | Partner directory + integrations marketplace |
| `support.qualiware.com` | `support` | Support hub, backed by Zoho Desk (EU) |

## Getting started

```bash
npm install
```

Start Postgres:

```bash
docker run -d --name qualiware-postgres -e POSTGRES_USER=qualiware -e POSTGRES_PASSWORD=qualiware-dev -e POSTGRES_DB=qualiware -p 5432:5432 -v qualiware-pgdata:/var/lib/postgresql/data --restart unless-stopped postgres:17-alpine
```

Then copy the environment template and fill it in:

```bash
cp .env.example .env
```

SQLite is still supported as a fallback — set a `file:` connection string — but
it locks the whole file per write, so it is single-developer only.

Then seed and run:

```bash
npm run seed
```

```bash
npm run dev
```

The seed is idempotent — run it as often as you like; it looks every document up
by its unique field and updates rather than duplicating.

Admin panel: <http://localhost:3000/admin> — `andreas.jensen@qualiware.com` /
`qualiware-dev`.

### Viewing the four properties locally

Each property has its own host — in development too, because `docs.localhost`,
`partners.localhost` and `support.localhost` resolve with no hosts-file entry in
current browsers.
Development therefore matches production exactly:

- <http://localhost:3000> — main marketing site
- <http://docs.localhost:3000> — Docs
- <http://partners.localhost:3000> — Partners
- <http://support.localhost:3000> — Support

Each sub-platform is a **separate site for search**, with its own canonical and
Open Graph URLs. That shapes link generation:

- **Within a property**, links are plain root-relative paths — the host already
  selects the tenant.
- **Back to the main site** — the wordmark, PLATFORM, PRICING, the footer
  columns — links are absolute, generated by `mainHref()` in
  `src/lib/links.ts`. Left root-relative, the logo on docs.qualiware.com would
  lead back to the docs home instead of to qualiware.com.
- **Sub-bar links** stay inside the current property and are never rewritten.

Point the whole set at production with one variable:

```
NEXT_PUBLIC_ROOT_DOMAIN=qualiware.com
```

The `/docs` and `/partners` path prefixes also still resolve, as a fallback for
an environment without wildcard DNS. Set `NEXT_PUBLIC_TENANT_MODE=path` there so
link generation emits matching prefixed URLs.

### Multi-tenancy

`@payloadcms/plugin-multi-tenant` scopes Pages, Docs, Categories, Partners and
Integrations. Editors pick a tenant in the admin panel and every list view and
relationship field filters to it.

**Tenant deletion is restricted to super admins.** The plugin cascades deletes
of all tenant-owned content when a tenant record is removed, so
`src/collections/Tenants.ts` locks `create`, `update` and `delete` to
`superAdminOnly`. Content editors cannot reach it.

### Docs hierarchy

Two trees, doing two different jobs:

- **Categories** carry the navigation tree — `parent` for arbitrary depth plus an
  explicit `order` number for manual sort within a sibling level. Payload has no
  drag-and-drop reordering across a flat collection list, so `order` is the
  mechanism; the collection's `defaultSort` is `order` and every nav query sorts
  by it.
- **Docs** carry the articles. They sit in a category and may also nest under one
  another via the Nested Docs `parent` field.

An article's public URL is its category path plus its own slug, e.g.
`/modelling/diagram-types/choosing-a-diagram-type`. The Nested Docs plugin builds
URLs from the `parent` chain only, which on Docs is article-to-article — so the
category portion is denormalised onto each article as `categoryPath` by
`src/collections/hooks/categoryPath.ts`, and `generateURL` prefixes the chain
with it. Renaming or moving a category re-saves every article beneath it, so
descendants follow their ancestor. There is a test for this in the git history;
to check it by hand, rename a top-level category in the admin panel and confirm a
grandchild article's URL changed.

`setCategoryPath` is a `beforeValidate` hook, not `beforeChange`: the plugin
*prepends* its own `beforeChange` hook, so anything registered there would run
after breadcrumbs had already been built.

### Audience gating

Everything is public by default: a deliberate reversal of the old gated
WordPress knowledge base. A document restricts itself by listing **`audiences`**
(`customer`, `partner`, or both); empty means public.

The field is optional and lives on **Docs, Pages and Posts** — defined once in
`src/collections/fields/audiences.ts`, so there is one thing for an editor to
learn and one rule enforcing it.

`audienceVisibility` in `src/access/` returns a *query constraint* rather than a
boolean, so the restriction is applied by the database on every read — pages,
search results, the sitemap and the REST API alike. There is no surface where
the rule can be forgotten. Restricted content returns **404**, not a sign-in
wall, because advertising that restricted material exists is itself a leak.

> This replaced an earlier `gated` boolean, which could only express "logged in
> or not". That is not enough with two distinct populations — a partner would
> have been able to read customer-only material.

**Gate on cost, not on value.** Content that is valuable to read is usually
worth more to us open: it ranks, it deflects support cases, and it lets a buyer
research quietly. Every gated page is invisible to search. Restrict only where
giving something away costs something real — partner commercial terms, deal
registration, scoping guidance, the implementation playbook.

Prefer **gating the action, not the page**: the support case form is readable by
anyone, but submitting requires a session. The page stays indexable and the
thing that matters is still protected.

In practice 2 of 39 docs articles are restricted, and no page or post is. That
is the intended state.

**This remains a proof of concept.** The partner portal is a non-functional
teaser. See **`ACCOUNTS.md` §3a** for the full mechanism, the support and
partner entitlement rules, and exactly what is enforced.

### Partner platform

Directory and marketplace only in this phase — **there is no partner login**. The
Partner Portal teaser on the partners homepage is a static locked-card visual
with a disabled sign-in button, standing in for a future gated phase.

Integrations are their own collection, so the marketplace works independently of
the partner directory.

## Page archetypes & E-E-A-T

Every marketing page declares a `pageType` archetype, and
`src/components/PageShell` gives each one distinct furniture — a coloured
archetype strip, and for regulation pages a facts panel and requirements table —
so a reader can tell what kind of page they are on before reading a word.

Pages also carry E-E-A-T fields: an `authorship` group (author, role,
credentials, named reviewer, `lastReviewed` date, first-hand `experienceNote`)
and a `sources` array where every external claim is cited with a date. Regulation
pages additionally carry the legal instrument, deadline, scope, penalty and an
article-referenced requirements table.

**`ARCHETYPES.md` is the contract** — read it before adding a page. It sets the
block skeleton per archetype, the citation rules (never invent a URL; never cite
a competitor claim), and the rule that Solutions pages link *down* into Platform
via `relatedCapabilities`, never the reverse.

Page `slug` is the **full path without a leading slash** (`solutions/nis2`), so
a page called `nis2` cannot answer `/solutions/nis2`.

Open one in the admin panel and copy its structure rather than inventing one:

Body elements are defined in `src/seed/docs/templates.ts`:

- **note blocks** — ice blue with a 3px dark-green left rule
- **code blocks** — deep green, monospace, horizontally scrollable
- bullet and numbered lists, links, and body paragraphs

Lexical's default feature set has no dedicated code-block node, so a fenced block
is a paragraph whose text carries the inline-code format; `RichTextBody` converts
that to a `<pre>`.

### Search

Docs search matches **titles, summaries and full body text**. Rich text is stored
as JSON, so a `like` query against `body` would match node names rather than
prose — each article therefore keeps a plain-text mirror in `searchText`,
maintained by a hook on every save. Searching a word that appears only
mid-article, such as `ontology` or `idempotent`, finds it.

Search is scoped to the property you are on: docs search covers documentation
only, and does not reach the marketing site or the help centre.

## SEO

Each property is a separate site for search and carries its own:

- **canonical and Open Graph URLs** — `metadataBase` is set per tenant, so
  `docs.qualiware.com/x` is canonical to itself, never to `qualiware.com`
- **`/sitemap.xml`** — its own URLs only. Docs lists articles and categories,
  Partners lists profiles, and gated articles are excluded because the query
  runs with `overrideAccess: false`
- **`/robots.txt`** — pointing at that property's sitemap

**Set `NEXT_PUBLIC_ALLOW_INDEXING=false` on any review deployment.** It switches
every property to `Disallow: /`. A staging copy of the marketing site competing
with the real one in search results is the expensive kind of mistake.

## Support & Zoho Desk

Support is now a **fourth property** — `support.qualiware.com`, tenant `support`,
green sub-bar, artboard 1n. It is built entirely from our own React components;
**Zoho Desk stays the system of record** and agent workflow does not change.

QualiWare is on the **EU data centre**, so the client targets
`https://desk.zoho.eu/api/v1` and `https://accounts.zoho.eu` for OAuth.

### What is wired

| Piece | How | Sign-in |
| --- | --- | --- |
| Help-centre search | `searchArticles()` → Desk KB, rendered in our components | No |
| Service status | Content — not a Desk feature | No |
| Response-time table | Content | No |
| Submit a case | Our form → server action → `createTicket()` → Desk `/tickets` | **Yes** |
| Ticket history | **Deliberately not built** — see below | — |

Reading the support property needs no account; **submitting a case does**. A
case attaches to a contract and its response times, and a typed email address
is a claim rather than proof — so identity comes from the session and the form
no longer has `name` or `email` fields at all.

#### Partners raising cases for their customers

A partner works the problem first and escalates to us when they cannot resolve
it, so a partner's case must name whose problem it is.
`Partners.supportedCustomers` lists the end customers a partner may raise for
and what they sold each one. If `supportLevelSold` is `none`, **QualiWare does
not provide that support** — the partner supports them directly, and the form
says so before anything is typed and refuses server-side if submitted anyway.

Allowed cases open with an entitlement block — end customer, support level, who
sold it, the Zoho account, and who raised it — so whoever picks it up does not
have to look the contract up. The subject is prefixed with the end customer's
name.

**Zoho Desk stays authoritative for the contract.** `supportedCustomers` mirrors
it so the form can refuse early, and will drift if nobody maintains it. Full
detail in `ACCOUNTS.md` §3a.

Ticket history is still not built. It needs a per-contact link into Zoho
(`accounts.zohoContactId`, below) and is best served by Zoho's own ASAP widget
rather than by rebuilding their views.

### Configuration

```
ZOHO_DESK_ORG_ID=...
ZOHO_DESK_CLIENT_ID=...
ZOHO_DESK_CLIENT_SECRET=...
ZOHO_DESK_REFRESH_TOKEN=...
ZOHO_DESK_DEPARTMENT_ID=...   # optional, routes new tickets
```

`src/lib/zohoDesk.ts` imports `server-only`, so a client secret leaking into the
browser bundle is a **build error** rather than a code-review question. Access
tokens are cached in module scope and refreshed a minute early, so a burst of
requests triggers one refresh rather than one per request. KB reads are cached
for five minutes because the Desk API is rate-limited per org.

### Without credentials

Everything renders and the flow is demonstrable end to end. The page shows a
"Preview mode" note, and a submitted case is stored in `form-submissions`
instead of creating a ticket — no fake success. If Zoho is configured but the
call fails, the case is **still stored** and the customer is told to phone for
anything production-critical, so a report is never lost to an upstream outage.

### Verify before wiring to the live desk

The client follows the documented v1 API but has **not been run against a live
EU org**. Confirm against Zoho's current documentation:

- the endpoint paths used (`/articles/search`, `/tickets`)
- the OAuth scopes needed (`Desk.tickets.CREATE`, `Desk.articles.READ`, …)
- that `orgId` is still the required org header
- the priority values accepted by `/tickets` — the form currently sends
  High/Medium/Low

Note also that `support.qualiware.com` currently serves the live Zoho help
centre. Cutting this property over means moving that DNS record, so run it on a
different host until you are ready.

## Front-end notes

The design handoff calls out four places where a naive responsive treatment
would fail, all handled:

- **Docs navigation** is a real collapsible tree, not a flat list. Each node keeps
  independent open/closed state (several open at once), state survives navigation
  within Docs via `sessionStorage`, and collapsed subtrees are not rendered at
  all — so a 150-category tenant mounts only what is visible. The tree is built
  from three queries regardless of size.
- **ComparisonTable** drops the table entirely below 900px and renders one card
  per capability row with a vendor chip selector. Never a horizontally scrolling
  table.
- **Mega-menu header** falls back to a mobile accordion, one section open at a
  time, 44px minimum rows.
- **PartnerDirectoryGrid** filters use a 280px rail on desktop and a filter
  *drawer* below 900px — not a reflowed rail. Chips apply immediately, so the
  drawer is not a form; SHOW RESULTS only closes it. Filter state is reflected in
  the URL so a filtered view is shareable.

### Design tokens

Everything visual comes from the tokens in `src/styles/globals.css`. Never
hardcode a hex that has a token.

Primary `#2b675b` · Ice Blue `#d2e9e3` · Dark Blue `#2e4163` · Neon Green
`#00ff00`. **Neon is accent-only and must stay under 5% of any screen** — arrows,
one CTA fill per screen, active underlines; never a large fill or background.

Typeface is PT Sans with a responsive H1–H6 + body/UI scale. Corners are square
everywhere: `border-radius` is 0 except 2px on buttons and 50% on status dots.
Card hover changes border colour only. There is exactly one shadow in the system,
on the mega-menu panel.

900px is the only breakpoint. Write the mobile rule first, then
`@media (min-width: 900px)`.

`CONVENTIONS.md` has the full house style for adding components.

## Authentication

Payload-native email and password, for two separate populations:

- **`users`** — CMS staff. Signs in at `/admin`.
- **`accounts`** — customers and partners. Signs in at `/sign-in`.

**There is no SSO.** No OIDC, no SAML, no social login. When you want it, Payload
supports custom auth strategies, and the entitlement model below does not change
— only the credential check is replaced.

### Entitlement

`accounts.audiences` is the primitive: `customer`, `partner`, or both. It gates
documentation, decides post-login routing, and tells the support form how to
attribute a ticket. It is **not** self-serve — field-level access restricts
updates to staff.

`audiences` on Docs, Pages and Posts mirrors it. Empty means public, which is
the default. Verified behaviour:

| Signed in as | partner-only | customer + partner | customer-only |
| --- | --- | --- | --- |
| anonymous | 404 | 404 | 404 |
| customer | 404 | 200 | 200 |
| partner | 200 | 200 | 404 |
| both | 200 | 200 | 200 |

Restricted articles **404 rather than showing a sign-in wall** — advertising that
restricted material exists is itself a leak. The same rule applies to search
results, the sitemap and the REST API, all confirmed by test.

### Session

End users get their own `qw-session` cookie. Payload derives its auth cookie name
from a *global* prefix, so `users` and `accounts` would otherwise share one and
signing in as a customer would silently end an admin session in the same browser.
Verification still goes through `payload.auth()`, so no JWT handling lives in
application code.

## Linking accounts to Zoho Desk

`accounts.zohoContactId` is the **authoritative support identity**. Whoever holds
it can read that contact's ticket history, so it must never be derivable from
anything a user controls.

### The rule

> An account holder may edit presentation facts about themselves.
> They may never edit anything that **asserts organisational identity or
> entitlement**.

Everything in the second category carries `access: { update: staffOnlyField }`.
Verified against a live signed-in session:

| Field | Self-editable | Why |
| --- | --- | --- |
| `fullName` | **yes** | presentation only |
| `email` | no | login credential *and* the Zoho bootstrap key |
| `zohoContactId` | no | grants read access to a contact's ticket history |
| `audiences` | no | entitlement — gates restricted documentation |
| `organisation` | no | asserts who you work for; used for ticket attribution |
| `partner` | no | claims a partner organisation |
| `supportTierHint` | no | would let someone display a tier they do not hold |

Field-level access is what enforces this — collection-level `update` still
allows an account to edit *itself*, which is what a profile page needs.

### Automatic linking, safely

`src/lib/zohoLink.ts` is the **only sanctioned writer** of `zohoContactId`. Four
rules, all enforced in code:

1. **Write-once.** Only ever set where it is currently null. Re-linking is an
   administrative act — otherwise changing an input could move someone onto
   another contact.
2. **Exact single match only.** Zoho's contact search is fuzzy, so results are
   filtered to a case-insensitive *exact* address match. Zero matches leaves it
   unlinked; two or more is reported as ambiguous. Never guess.
3. **Server-side only.** The address searched is the **stored** account email —
   which is staff-only — never a value from the request.
4. **Audited.** Every automatic link is logged with the account, address and
   contact id.

```bash
npm run zoho:link
```

Dry run by default: it reports what *would* happen and writes nothing. Add
`-- --commit` to apply. Dry-run-first is deliberate, because this writes the
field that governs whose support history a person can read.

### Provisioning new people

Safest first, and the invite flow is the one to build:

- **Invite token.** Staff create the Zoho contact; the system emails a signed,
  single-use token bound to that contact id; the user sets a password and the
  account is created **already linked**. The user never types the value that
  determines access. Needs the email adapter.
- **Staff-provisioned.** Staff paste the contact id during onboarding. Works
  today, no dependencies.
- **Auto-link by email.** Only safe when the address is *verified*, the link is
  null, and it happens once server-side — which is what `zoho:link` does. It is
  strictly weaker than an invite, because it trusts the address.

## Performance, and a dev-mode trap

Measured on the production build, warm: **11–45ms** per page across all four
properties. `npm run dev` is far slower — 1–3 seconds — because Turbopack
recompiles per route. Judge performance from `npm run build && npm start`, never
from dev.

Two things worth knowing:

- **Never `npm install server-only`.** It is a marker package whose `main` entry
  *throws*; only the `react-server` export condition maps to a no-op stub.
  Installing it crashes the Next dev render worker with
  `Jest worker encountered 2 child process exceptions`, which then presents as
  random 500s and slow pages. Next provides its own alias, so the bare
  `import 'server-only'` works without the package. `src/lib/zohoClient.ts` uses
  a runtime `typeof window` guard instead, because it must also be reachable
  from CLI scripts.
- **`populate` matters on related pages.** `resolvePath` fetches pages at
  `depth: 2`, and a Solutions page links to five Platform pages. Without a
  `populate` restriction each of those arrived with its whole block tree and its
  own relations — the homepage took 4.3s in dev. Related pages are only rendered
  as a title, a link or a card, so only those fields are populated.

If a dev server ever hangs rather than erroring, check for an orphaned process
holding port 3000: Payload's schema push prompts interactively, and with no TTY
it waits forever. `taskkill /PID <pid> /F` on Windows.

## Before you deploy

### Blocking — auth will misbehave without these

1. **Set `SMTP_HOST`.** The nodemailer adapter is wired but only attaches when
   that variable is present, so a bare install logs
   `WARN: No email adapter provided` and writes mail to the console — meaning
   *"forgot password" does not work*. That warning is expected in development
   and unacceptable in production, because password reset is the only way back
   into an account. See `.env.example` for the full `SMTP_*` set.
2. **Delete the demo accounts.** `customer@example.com`, `partner@example.com`
   and `both@example.com` all use the password `qualiware-dev`. They are seeded
   fixtures, and one of them holds partner entitlement. Remove the seeded
   `supportedCustomers` from Devoteam and CGI Canada at the same time — they are
   invented contracts.
3. **Rotate `PAYLOAD_SECRET`.** The `.env` value is a development secret.
   Rotating invalidates every existing session, so do it before launch, not after.
4. **Set `SESSION_COOKIE_DOMAIN=.qualiware.com`** or sign-in will not carry
   across the four properties. Unset locally on purpose — browsers do not share
   cookies across `.localhost` subdomains.

### Blocking — infrastructure

5. **Media is on local disk.** The database is Postgres, but uploads are not —
   they need a persistent volume, or object storage if this ever runs on more
   than one host.
6. **Wildcard DNS** for `docs.` / `partners.` / `support.`, or set
   `NEXT_PUBLIC_TENANT_MODE=path`.
7. **`NEXT_PUBLIC_ALLOW_INDEXING=false` on review deployments.**

### Worth knowing

- Brute-force lockout is Payload's default: five failed attempts, then a
  ten-minute lock. Confirmed working. There is no lockout notification, so a
  locked customer will simply be stuck until it expires or staff clear it.
- Sessions last eight hours with no refresh — users are signed out abruptly.
- `supportTierHint` is **display only**. The contract in Zoho Desk decides the
  real SLA; never compute entitlement from that field.
- The support case form does not yet use the session identity for Zoho
  attribution — it still takes a typed email.

## Known limitations

- **Tier table, docs orientation cards and the portal teaser are static.** They
  are prop-driven components rendered by `PartnersHome` / `DocsHome`, not blocks,
  so changing their copy needs a deploy. All three are ready to be promoted to
  blocks if editors need them.
- **`/directory` and `/integrations` are reserved paths.** They are guarded routes
  that 404 outside the partners tenant, so the main site cannot have a page at
  either slug.
- **Search is title/excerpt matching**, not full-text. Article bodies are not
  indexed. Swap in `@payloadcms/plugin-search` or an external index when the
  corpus justifies it.
- **A gated article 404s** for anonymous visitors rather than showing a sign-in
  wall. That is correct and safe, but a friendlier interstitial would be better
  once the gating feature is actually used.
- **Media is unresolved by design.** Every image is a labelled placeholder
  carrying the shot brief from the handoff; no assets were invented.

Flagged in the handoff and carried into the seed as-is:

1. **Analyst claims.** The Gartner callout states Leader in the EA Tools MQ for

   across 110 Peer Insights reviews. The live site currently says Visionary

2. **Competitor cells** on the comparison page all read "To verify" by design.

3. **Pricing tiers** (Foundation / Connected / Enterprise) are proposed names,
   not existing SKUs. No prices are shown anywhere.
4. **Partner records, case-study numbers and service-status content** are

### Bylines and experience claims are placeholders

**Every author and reviewer name in the seed is invented.** So is every figure in
an `experienceNote` (engagement counts and start dates). They demonstrate the
E-E-A-T structure; they are not facts.

Before launch, replace each with a real, consenting member of staff and a claim
that person will stand behind. An invented byline is worse than no byline — it is
the specific thing E-E-A-T is meant to detect.

### Regulation pages need legal review

`solutions/nis2`, `solutions/dora`, `solutions/csrd` and `solutions/iso-27001`
state dates, article references and scope. They were drafted carefully and
deliberately stay qualitative where the answer depends on member-state
transposition or entity classification — but they are not a substitute for legal
review.

Specifically confirm, against the consolidated instruments:

- **NIS2** — entry into force 16 January 2023 and transposition deadline
  17 October 2024; repeal of Directive (EU) 2016/1148; that the 24-hour early
  warning and 72-hour notification both sit in Art. 23(4) rather than being split
  across 23(3) and (4); Art. 21(1) and 21(2)(a)–(d); Art. 20; the Annex I/II
  sector paraphrase; and that some entities are in scope regardless of size.
